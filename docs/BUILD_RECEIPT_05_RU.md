## Что проверено в ночном сценарии

Использован **настоящий слышимый звук для сна**, не пустой WAV. `sleep.wav` — оригинальный 8-секундный шум; RMS 0.0804 до программной громкости 0.25. Воспроизведение зациклено через AVAudioPlayer и `.playback`/`audio` фон.

1. Приложение запросило AlarmKit и получило разрешение.
2. Запущено воспроизведение, появились искусственные активные статусы.
3. XCTest отправил Home, затем IDB аппаратное событие LOCK. `locked.json` фиксирует время, `screen-locked.png` показывает настоящий экран блокировки симулятора.
4. После LOCK продолжились проверки, `background=true`, `audio_playing=true`.
5. `lease.extended` дважды: новый резерв подтверждался до отмены предыдущего.
6. При искусственном отбое появился `release.scheduled`.
7. После этого AlarmKit сообщил `.alerting`: событие `release.alerting`.
8. `screen-final.png` показывает системный экран «Світанок · источник сообщает отбой», а не резерв «проверка прервалась».
9. Все доказательства: `docs/v05-night/`.

Реальная доставка данных UA Siren, громкость/динамик физического телефона и работа 6–12 часов этим искусственным коротким тестом **не подтверждены**. Ночное устройство может прервать воспроизведение (звонок, другое аудио, закрытие процесса, условия iOS). Последний короткий системный резерв сохраняется и может прозвучать при продолжающейся тревоге.

## Альтернативный метод

Проверялась BGContinuedProcessingTask. После исправления регистрации конкретного идентификатора симулятор всё равно отказал: BGTaskSchedulerErrorDomain code 1. Успеха этого варианта нет; он не используется успешным аудиотестом. Нельзя заменять эту неудачу ручным/private-API запуском задачи и выдавать это за ночную работоспособность.
